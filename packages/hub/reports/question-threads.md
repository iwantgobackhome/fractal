# Hub question threads

Implemented ask/explain `threadId` persistence and bounded prior user/assistant messages. Only completed, nondeleted question/explanation entries for the same paper and thread are included, sorted by createdAt then ID. The current requestId is excluded; context is captured before the current entry is admitted. Explanations use `Explain <kind> on page N`; selected quotes are limited to 800 characters, prior questions to 4,000, and answers to 4,000 with an ellipsis. At most six complete pairs and 12,000 content characters survive, dropping oldest pairs first. Without threadId, no history query or prior messages are added.

The existing AiProvider interface accepts message arrays. Both CLI adapters already serialize these as `user: ...` / `assistant: ...`, so the implementation reuses their formatting. The current 4,000-character question is retained in full, independently of the prior-context budget. CLI providers send prompt text through stdin without an additional question-length validator. Existing paper context keeps its existing 600,000-character cap (explanation page text: 30,000); model-specific token limits remain governed by the existing provider path, and this change adds at most 12,000 content characters plus role separators rather than unbounded history.

SQLite foundation get/list/put parses historyEntrySchema and stores the entire record as JSON. History APIs return those records; pull fetches them via getHistory; push validates syncPushSchema/historyMutationSchema and forwards the complete entry through putHistory. The shared schema already includes context.threadId, so no migration or shared-contract change was necessary. The HTTP regression test covers ask and explain persistence, SQLite reopening, list history, sync pull, offline sync push and subsequent pull, mixed ask/explain conversation messages, and single-shot behavior.

Language resolution is unchanged. UI usePreferences reads hub.preferences() and updates the full preference record with hub.savePreferences(), backed by GET/PUT /api/preferences and SQLite preferences JSON. A request override wins; otherwise answerLanguage() uses store.getPreferences().answerLanguage. `auto` means match the question language for ask; for explain (no user question passed to language resolution), it uses preferences.uiLanguage. The non-SQLite fallback is answerLanguage auto and uiLanguage ko. Existing HTTP tests verify a saved global preference is used when the request omits answerLanguage; per-request overrides do not mutate preferences.

Validation: built the ignored shared distribution required by workspace package exports, then `npm run typecheck` passed across shared, hub and UI. Targeted thread-context/provenance suites passed all 14 tests. Full `npm test -w @fractal/hub`: 257 passed, three known baseline failures only: claude-usage shutdown cancellation and publication/open altered-cache open/link localized-message assertions. No other failures remain. No UI, Android, shared sources, push, tags or release changes were made.
