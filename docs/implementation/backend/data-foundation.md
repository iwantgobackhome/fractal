# Backend data foundation contract

This stage covers persistence, folders, history and sync. Discovery providers and related-paper reliability are a later dispatch. All page numbers below are **one-based physical PDF pages**; `Block.pageOrdinal` is an ordinal within a page, never a page index. Block regions already carry normalized positions and `sourceText`, and remain available in the existing `/api/papers/:key` API. These coarse regions cannot guarantee character/word dragging on older Android APIs; the concrete subsequent extraction task is [PDF text selection follow-up](pdf-text-selection-followup.md).

## Library and folders

`LibraryRecord` retains its existing fields and gains optional fields for old-client compatibility: `saved?: boolean`, `savedAt?: string|null`, `lastReadAt?: string|null`, `readProgress?: ReadProgress|null`, `rev?: number`, `deviceId?: string`. New hub output always supplies these fields. New ingestion creates bibliography metadata with `saved=false`, `savedAt=null`, `lastReadAt=null`, `readProgress=null`; ingestion does not imply reading. Explicit save uses `PATCH /api/library/:key {saved:true}`. Removing save uses `{saved:false}` or `DELETE /api/library/:key`; both retain PDF, annotations, metadata, progress, and history. The existing destructive `DELETE /api/papers/:key` remains an explicit local paper deletion API.

`ReadProgress = {page:number, fraction?:number, blockId?:string, scrollOffset?:number}`. `fraction` is overall reading completion from 0 to 1; `scrollOffset` is viewport vertical position within that page from 0 to 1. `blockId` is an optional anchor ID, not an ordinal. The hub checks page bounds when page count is known. `POST /api/papers/:key/read {readProgress?:ReadProgress|null}` records an actual view with a server timestamp. `PATCH` also accepts `lastReadAt` and progress for offline clients; lastReadAt never decreases. Old migrated entries get no fabricated lastReadAt or progress.

`GET /api/library` retains the full bibliography response. `?view=saved` returns saved entries, `?view=recent` returns entries with lastReadAt sorted newest first. These views can overlap. `POST /api/library/metadata` accepts a `LibraryRecord` and publishes a new bibliography entry without a PDF or reader Paper; absent saved defaults false. Use PATCH for subsequent edits.

Metadata-only duplicate matches do not mean a reader Paper exists. Ingestion materializes the same canonical reader key while retaining saved state and metadata memberships/tags. A catalog key that differs from the acquired reader identity is rejected before saving an unrelated duplicate; catalog-to-reader association is a later discovery dispatch, and must preserve stable references/history rather than rename catalog entries or relax reader identity checks.

Collections remain the multiple-folder-membership field on a paper: `collections:string[]`. Tags remain `tags:string[]`. IDs migrate unchanged. `Collection` / `Folder` adds optional `parentId:string|null`, `updatedAt:string`, `deleted:boolean`, `rev:number`, `deviceId:string`. Old collections become roots. Both `/api/library/collections` and `/api/library/folders` support GET list and POST `{id,name,parentId?}`; `/:id` supports PATCH `{name?,parentId?}` and DELETE. Omitted parent preserves the old parent. Root parent is null. Cycles and missing/deleted parents are rejected. Deleting a folder tombstones it, promotes immediate child folders to the deleted folder's parent, removes just that membership from every paper, and retains every paper. Tombstoned IDs cannot be reused. Existing orphan memberships are preserved during migration and unrelated edits.

## Persistent history

Existing POST `/api/papers/:key/ask`, `/api/papers/:key/explain`, and `/api/library/ask` retain their SSE responses and accept optional `requestId:string` (1–100 chars). A request is written before provider selection/generation. SSE opcodes remain `delta`, `done`, `error`; events gain optional `historyId`. The initial event is `{type:'delta',text:'',historyId}` so a client can immediately bind a panel to a durable ID. Stream consumption/closure never cancels generation or deletes history. Explicit cancellation is a separate operation. Partial text, errors and completion are persisted. A restart settles unfinished generation as failed with a retryable interruption error; shutdown also records interruption, rather than user cancellation.

`HistoryEntry = {id,paperKey:string|null,kind:'question'|'explanation'|'conversation',question,text,status:'pending'|'running'|'completed'|'failed'|'canceled',createdAt,updatedAt,completedAt:string|null,requestId:string|null,context,answer:AiAnswer|null,error:{code,message,retryable}|null,latex?:string,conversation?:{conversationId,messages},rev,deviceId,deleted}`. `context` holds optional `{page,rect,selectedText,explanationKind:'figure'|'equation'|'table'|'text',selection:ModelSelection}`. All timestamps are ISO UTC. Paperless/library questions use paperKey null. Legacy chat conversation history retains original messages and IDs.

GET `/api/library/history` returns `{history:HistoryEntry[]}` for all history; GET `/api/papers/:key/history` returns that paper's history. Optional `?kind=` and `?status=` filter both lists. `/:id` GET returns `{history:HistoryEntry}`; `/:id/cancel` POST explicitly cancels and persists canceled state, and `/:id` DELETE explicitly tombstones the history (stopping active work). Encode IDs in path segments. Tombstones are absent from normal lists/details but present in sync. Existing `/api/papers/:key/chat` active-conversation GET/POST/DELETE/cancel APIs retain their behavior. Clearing that active conversation archives its previous history rather than erasing the history list; deleting a history explicitly can clear the corresponding active conversation. UI closure must use neither DELETE nor cancel.

Identical requestId plus scope `(paperKey,kind)` reattaches to a running request or replays a settled result, without new generation. Changed question/context under the same ID is rejected. A deleted request requires a new ID. The input model selection belongs to context for replay validation.

## Synchronization

GET `/api/sync/pull?since=N` retains `{cursor,papers,annotations}` and adds `{folders,history,deletedPapers}`. Folded records carry revisions; folder/history deletions carry tombstones. A hard paper deletion appears in deletedPapers. Cursor is the hub append-only local sequence. Each pull is a snapshot without asynchronous gaps.

POST `/api/sync/push` retains `annotations:Annotation[]` (old annotation-only payloads remain valid) and accepts optional arrays:

- `papers:[{paperKey,baseRev,patch:LibraryPatch,deviceId,requestId}]`
- `folders:[{id,baseRev,patch:{name?,parentId?},deleted?:boolean,deviceId,requestId}]`
- `history:[{entry:HistoryEntry,baseRev,requestId}]`

Folder creates use baseRev 0; parents should precede children within the batch. Folders are applied before papers. Other entities use the last pulled revision. Metadata writes use compare-and-swap, not client wall-clock last-writer-wins. Rejection returns the authoritative current record so clients can rebase independent saved, membership, tag and progress patches with a fresh request ID; clients must retain their unsent local patch. Request IDs are unique across metadata mutation kinds per device. Exact retry returns the original receipt; reused ID with different data is rejected. Each successful mutation and its change log/receipt commit atomically. History imports must be settled; active hub generation cannot be overwritten by an offline entry. Legacy conversation history is controlled through `/chat`.

Response retains `{results,cursor}` for annotations and adds `serverHead` and `metadataResults:[{kind:'paper'|'folder'|'history',id,applied,conflict,rev,current}]`. **Push cursor and serverHead are server heads, not consumed checkpoints. Never advance a client's stored pull checkpoint from either push response field.** Only a pull whose whole payload was durably applied can advance the checkpoint; otherwise concurrent changes between pull and push are skipped. Conflict current can be null for missing records. Annotation timestamp/device-ID conflict semantics and geometry stay unchanged. Explicit hard paper deletion now publishes annotation/history tombstones alongside deletedPapers, so other devices can remove retained local resources. Mutation batches can apply successful items before a later invalid item fails; retry metadata with the same request IDs, and retry annotations with unchanged timestamp/device identity.

Memo gains optional `collapsed:boolean` and `color:'yellow'|'green'|'blue'|'pink'`; existing nullable normalized `rect` supplies sticky position. Defaults are a client presentation choice. This change introduces no translated/original annotation mapping. Android Room migration and client offline queue/checkpoint implementation belong to D.

## Migration decisions

SQLite migration 11 is transactional and preserves old rows, PDFs, annotations, translations, jobs, metadata and memberships. Old bibliography entries become saved=true, savedAt=addedAt, lastReadAt=null and readProgress=null. Collections gain JSON metadata with null parent. Legacy conversations are copied to history without deleting/changing active conversation data. The history table persists request IDs and tombstones; mutation_receipts persists metadata idempotency receipts. Legacy JSON import likewise marks imported shelves saved. The regression fixture is created using the real pre-foundation SQLite schema and PDF blob layout rather than constructing a new-schema database and stripping fields.
